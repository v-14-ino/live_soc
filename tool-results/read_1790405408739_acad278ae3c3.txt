    94→socket.io client lifecycle (path `/`, single `'message'` event channel):
    95→- On connect: emit `{ type: 'hello', sessionId: '', serverTime }` immediately. (`sessionId` is empty at hello time because no subscription yet — frontend should treat hello as a connection-ack only.)
    96→- Client commands arrive as `socket.on('message', cmd: WSClientCommand)`. Handler dispatches on `cmd.type`:
    97→  - `subscribe` — looks up `sessionManager.getActive(sessionId)`. If found: registers a per-socket callback via `sessionManager.subscribe(sessionId, cb)` that calls `socket.emit('message', msg)` for every broadcast; joins room `session:${sessionId}`; then sends an immediate burst so the client has current state: `session_status` → `assessment_update` → `kpi` → `network_activity` → last 50 `event` messages → last 50 `alert` messages → all current `offense_scenario` and `defense_scenario` messages. If not found: emits `session_status` with `status: 'stopped'` + an `error` message with code `SESSION_NOT_ACTIVE`.
    98→  - `unsubscribe` — calls `sessionManager.unsubscribe(sessionId, cb)`, leaves the room, removes from per-socket subscription map.
    99→  - `ping` — responds with `{ type: 'heartbeat', serverTime }`.
   100→  - `pause_stream` / `resume_stream` — flips a per-socket `paused` flag (server keeps broadcasting; client handles visual pause). Sends a `log` message acknowledging.
   101→  - Default (unknown command type) — emits `error` message. Exhaustiveness-checked via `never` cast.
   102→- On `disconnect`: iterates the per-socket subscription map and calls `sessionManager.unsubscribe(sessionId, cb)` for each — guarantees no dangling subscribers that would `socket.emit` to a dead socket.
   103→- Per-socket state stored in a `WeakMap<Socket, SocketState>` so it's GC'd when the socket is.
   104→- Heartbeat interval: every 25s, `io.emit('message', { type: 'heartbeat', serverTime })` to all connected sockets.

   576→### Caveats for next agents
   577→- **PDF generation is client-side via `window.print()`**: per the task spec's explicit fallback (the pdf skill recommends ReportLab which is Python-only and unavailable in this Next.js client-side app). After this fix, all settings fields correctly hydrate from the DB. The fix is backward-compatible at the API level — only the TypeScript types changed.

   580→- **`GET /api/reports/<reportId>` now does extra DB work**: it re-assembles the full `ReportData` from the still-persisted session. If the session row was deleted (e.g. via the new "Clear All History" button), `data` falls back to `null` and the Reports view shows a graceful "Report Data Unavailable" empty state instead of crashing.

   818→## Architecture
   819→
   820→The status update flow is:
   821→
   822→```
   823→Browser (Ack/Resolve button click)
   824→  → api.updateAlertStatus(sessionId, alertId, status)
   825→  → PATCH /api/monitoring/<sessionId>/alerts  (Next.js route, body { alertId, status })
   826→  → PATCH http://127.0.0.1:3003/internal/alerts/<alertId>  (monitor-service, body { sessionId, status })
   827→       │
   828→       ├─ If session is still ACTIVE in sessionManager:
   829→       │    sessionManager.updateAlertStatus(sessionId, alertId, status)
   830→       │      1. Update active.recentAlerts[idx].status (in-memory)
   831→       │      2. db.alert.update({ where: { alertId }, data: { status } })  (DB persist)
   832→       │      3. auditLog("info", "alert", "Alert <alertId> status → <status>", {...})
   833→       │      4. broadcastLocal(active, { type: "alert", alert: updatedAlert })  (WS broadcast)
   834→       │    → returns { ok: true, alertId, status } or 404 if alert not in recentAlerts
   835→       │
   836→       └─ If session is NOT active (historical):
   837→            db.alert.update({ where: { alertId }, data: { status } })  (DB-only)
   838→            auditLog("info", "alert", "Historical alert <alertId> status → <status>", {...})
   839→            → returns { ok: true, alertId, status } or 404 if Prisma update fails (record not found)
   840→```
   841→
   842→The WS broadcast reaches all subscribed browser clients. The `use-monitor-ws` hook now uses `upsertAlert` (instead of `pushAlert`) for incoming `alert` messages, so a status-update broadcast replaces the existing alert entry instead of being added as a duplicate. The operator who clicked the button also sees the update via this round-trip (the local `updateAlertStatus` store action is fired optimistically on success).

   961→## Caveats for next agents
   962→- The `pushAlert` store action is kept for backward compatibility but is now only used by code paths that intentionally want to always-prepend (none in the active codebase after this change — `use-monitor-ws.ts` now uses `upsertAlert`). If you add new alert sources, prefer `upsertAlert` to avoid duplicates when an alert with the same `alertId` already exists.
   963→- The historical alert PATCH goes through the monitor-service even though the session is no longer active. This is intentional: it keeps a single endpoint for both active and historical updates, and the monitor-service is the only process with `db` access in the current architecture (Next.js API routes also have `db`, but routing through the monitor-service means we don't need a second Prisma client connection per request and the audit log entries all flow through the same `monitor-service` / `alert` module). If the monitor-service is down, historical alert updates will return 503 — the operator gets a clear toast. If you want to make historical updates resilient to monitor-service downtime, you could add a DB-only fallback in the Next.js route itself.
   964→- The alert `status` field in the DB schema is `String @default("active")` (see `prisma/schema.prisma` Alert model). No schema migration was needed — the field already existed.
   965→- The `totalAlerts` counter in the store (`state.totalAlerts`) is only incremented when a NEW alert is added (via `pushAlert` or `upsertAlert` when the alertId doesn't already exist). Status updates do NOT bump this counter, which is correct — it reflects "total alerts ever raised in this session", not "current list length".
   966→- The KPI `critical/high/medium/low/info` counts in `computeKpi()` count EVENTS by severity, not ALERTS. The alert count badges in the `LiveAlerts` panel are computed separately from `state.alerts` and only count ACTIVE alerts. These two systems are independent — don't confuse them.
   967→- The `AlertActionButtons` component has its own local `busy` state, so each card's buttons can be independently disabled while a PATCH is in flight. If the user clicks Ack on card A then immediately clicks Resolve on card B, both PATCHes run concurrently — this is fine because they target different alertIds.
